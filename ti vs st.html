Objective and Measurement Method

Objective

  • Compare linked flash and RAM footprint of 12 semantically mapped projects.
  • Verify equal optimization baseline across both platforms.
  • Identify where STM32 is stronger and where it remains weaker.
  • Interpret differences using only map-file evidence.

Measurement

  • RO code: readonly code memory
  • RO data: readonly data memory
  • RW data: readwrite data memory
  • Flash = RO code + RO data
  • RAM = RW data
  • Both platforms reserve a 512-byte stack in these maps.

Fairness rules

  • Like-for-like scenario and role pairing
  • Controller/master matches controller/master
  • Responder/target/peripheral matches responder/target/peripheral
  • DMA, interrupt, and polling modes are not mixed
  • Startup/vector-table bytes are included as real deployable image cost
  • Startup, linker, HAL, LL, CMSIS, middleware, and vendor internals were not modified

Where STM32 Is Strong

Scenario wins

  • ADC timer trigger
  • I2C DMA controller
  • I2C DMA responder
  • I2C polling controller
  • I2C polling responder
  • UART printf
  • USART loopback

Main reasons

  • Minimal app-owned initialization
  • Removal of unused buffers and dead state
  • Internalized helpers enabling better compiler folding
  • Lower RW data in many communication scenarios

Key point

STM32 is not inherently worse in executable code size. In some scenarios, STM32 RO code is smaller than MSPM33 RO code. Several remaining flash losses come from fixed RO-data overhead rather than inefficient application logic.

Main causes

  • Required interrupt event/error infrastructure
  • More explicit application-owned control logic, especially in SPI DMA controller

Case Study — GPIO Toggle

Observed result

  • MSPM33 flash: 656
  • STM32 flash: 772
  • Delta: +116 bytes, +17.7%

Important nuance

  • MSPM33 RO code: 380
  • STM32 RO code: 312
  • STM32 code is actually 68 bytes smaller

Why STM32 still loses

  • MSPM33 RO data: 276
  • STM32 RO data: 460
  • Fixed RO-data difference: 184 bytes

This is a structural startup/vector-table penalty. The GPIO case is too small for the lower STM32 code size to overcome the fixed RO-data overhead.

Case Study — SPI DMA

Controller

  • MSPM33 flash: 1,704
  • STM32 flash: 2,151
  • Delta: +447 bytes, +26.2%
  • RAM delta: -36 bytes, -6.1%

Peripheral

  • MSPM33 flash: 1,876
  • STM32 flash: 1,940
  • Delta: +64 bytes, +3.4%
  • RAM delta: -40 bytes, -6.8%

Why STM32 is worse here

The STM32 application explicitly carries GPIO, DMA, SPI, NVIC, EOT, DMA-error, compare, LED, and delay behavior in the application object. MSPM33 resolves more of this behavior through compact linked DriverLib modules. This remains STM32’s largest flash weakness in the portfolio.

Fairness Status and Limits

What is solid

  • All 12 active projects use the same high/size IAR baseline.
  • DMA, interrupt, and polling modes are paired like-for-like.
  • Controller/master and target/responder/peripheral roles are paired like-for-like.
  • Generated vendor files and internals were not modified.
  • All modified projects build with zero IAR errors and zero warnings.

Current limits

  • Hardware runtime equivalence has not yet been revalidated.
  • STM32Cube tree provenance is based on local evidence path.
  • MSPM0 numbers are from existing map artifacts, not rebuilt in this pass.
  • These are footprint results, not throughput or peripheral-quality claims.

Final message

  • MSPM33 has the smaller aggregate flash footprint by 514 bytes or 2.8%.
  • STM32 has the smaller aggregate RAM footprint by 338 bytes or 5.0%.
  • STM32 is strongest in ADC, I2C DMA, I2C polling, and small UART/USART cases.
  • STM32 remains weaker where fixed startup/vector overhead or explicit application-owned control paths dominate, especially GPIO and SPI DMA controller.
