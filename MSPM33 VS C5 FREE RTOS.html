Executive Summary

Across the 3 FreeRTOS benchmark scenarios, STM32C5 consistently produces the smaller linked flash image, with a measured reduction of about 28–30% versus TI MSPM33 after TI's FreeRTOS configuration was aligned to remove an avoidable fairness artifact. RAM is effectively tied, with STM32 only 56–76 bytes higher depending on scenario.

Observed runtime logs also show higher raw throughput on STM32 in all 3 scenarios. However, that runtime result must be treated as observed behavior only, not a final capability conclusion, because CPU clock parity and cross-target codegen equivalence were not fully verified.

Why the Flash Gap Exists

1. Application Layer

The benchmark application logic is essentially comparable across vendors. In multiple cases, object-level evidence shows only a few bytes of difference, supporting that the app itself is not the main driver of the measured gap.

2. Middleware Layer

A significant fairness artifact on TI was removed by aligning FreeRTOS feature flags with STM32. That reduced the middleware gap from roughly 46–50% down to roughly 16–17%.

3. Low-Level / Library Layer

The largest remaining flash delta is dominated by TI's vsnprintf() path, which pulls in a much larger full printf formatter. This is the main remaining explanation for the measured flash difference.

Important nuance: the remaining low-level gap is not purely a driver-library problem. In isolation, TI DriverLib is lighter than STM32 HAL in direction, but TI's measured low-level bucket still becomes larger overall because of the standard-library formatting path.

Observed Runtime Anomaly

TI cooperative_scheduling ERROR at 90 s / 120 s

The TI cooperative log shows an ERROR at the 90,000 ms and 120,000 ms marks only. This was traced to the benchmark's own integer-truncated average and ±1 tolerance logic, not to a confirmed scheduling defect.

  • The condition occurs when integer division truncation places one thread count just outside the allowed bound.
  • The spread is of the same order as non-error windows.
  • STM32 did not show the same artifact in the shorter capture window, but a longer STM32 run could plausibly hit it too.

Classification: Benchmark-design artifact, not a confirmed functional gap.

Executive caution: The footprint conclusion is solid. The runtime conclusion is provisional and should be described as observed throughput under current test conditions, not as a final platform-performance ranking.

Recommended Actions

1. Close the runtime blocker

Measure or normalize actual CPU clock frequency on both targets. This is the main blocker to converting observed throughput into a defensible capability conclusion.

2. Remove TI printf inflation

Replace TI's vsnprintf() path in benchmark_port.c with a lightweight formatter similar in scope to the STM32 implementation. This is expected to recover about 6.8 KB of flash.

3. Optional STM32 footprint reduction

If needed, evaluate HAL-to-LL migration for STM32 low-level drivers. This requires approval because it changes protected low-level implementation surface.

Management Summary

  • STM32C5 is the confirmed flash-footprint winner across all 3 FreeRTOS benchmark scenarios.
  • The measured flash advantage remains substantial even after fairness alignment on TI's FreeRTOS configuration.
  • RAM is effectively tied; differences are very small.
  • The application layer is near-equivalent and is not the primary cause of the measured gap.
  • The dominant remaining flash driver is TI's standard-library formatting path, not just vendor driver weight.
  • Observed runtime throughput favors STM32 in all logs captured, but that is not yet a final capability claim.
  • Next step for a runtime conclusion: verify or normalize clock frequency and accept or resolve the remaining codegen-risk caveat.
